# KIDRA

KIDRA manages an electronic part library for KiCad. The web app is where you edit the
**parts** (value, category, symbol, footprint, manufacturer, ratings, distributor numbers,
tags and attachments such as datasheets, manuals, app notes, images and 3D models) and the
**master data** they refer to: categories, designators, symbols, footprints, units,
manufacturers, distributors and tags. The backend is a custom PocketBase build that stores
the data, syncs the KiCad library repository, serves the KiCad HTTP library API and serves
the built app itself.

- [ARCHITECTURE.md](ARCHITECTURE.md): how the code is organised, backend and CI/CD.
- [deploy/README.md](deploy/README.md): operator guide (Proxmox VMs, runner, backups,
  native installs, reverse proxy).

## Repository layout

```

backend/             Go module `kidra`: PocketBase + Kidra routes, library sync, kicad-cli
  pb_migrations/     JS migrations (schema + bootstrap settings), applied on start
  ui/dist/           SPA build output (git-ignored), embedded with -tags embedui
  third_party/       vendored s-expr parser (go.mod `replace`)
deploy/              operator files: VM scripts, CI deploy script, env files, proxy
                     configs, systemd unit, Windows guide
.github/workflows/   ci.yml, docker-pr.yml, main.yml, release.yml
release-please-config.json, .release-please-manifest.json
                     release-please configuration and current released version
version.txt          current released version (maintained by release-please)
CHANGELOG.md         release notes (generated by release-please)
LICENSE              GNU AGPL v3
Dockerfile           images: full (default, with kicad-cli) and slim

compose.build.yaml   override that builds the image from this checkout
.env.example         reference for every compose and application variable
.vscode/launch.json  backend, frontend and browser debug configurations
```

## Prerequisites

- Node.js 26 (see `.node-version`) and pnpm (version pinned by `packageManager` in
  `frontend/package.json`). `frontend/.npmrc` sets `engine-strict=true`.
- Go (version in `backend/go.mod`).
- Optional: [kicad-cli](https://docs.kicad.org/master/en/cli/cli.html) (KiCad 8 or newer)
  for symbol/footprint SVG previews, and `git` on `PATH` for the library sync.

## Development setup

1. Start the backend on port 8090:

   ```sh
   cd backend
   go run . serve
   ```

   Data goes to `backend/pb_data/` (git-ignored). On the first start the migrations in
   `backend/pb_migrations/` build the schema and apply the bootstrap settings (see
   [PocketBase settings](#pocketbase-settings)). Open http://127.0.0.1:8090/_/ to create a
   superuser (or set `KIDRA_ADMIN_EMAIL` / `KIDRA_ADMIN_PASSWORD` before the first start),
   then create a user in the `users` collection to log in to the app with (the
   collections' API rules expect the role `admin` in its `roles`).

   The backend clones (or pulls) and parses the library repository in the background;
   without network access it starts anyway and retries on the next pull.

   **Schema changes:** under `go run`, Automigrate is on: every collection change made in
   the dashboard writes a JS migration into `backend/pb_migrations/`. Commit those files
   together with the code that needs them, and run `pnpm types` in `frontend/`. Automigrate
   is only enabled when the executable lives in the temp directory (as with `go run`); a
   binary built with `go build` only applies migrations. The VS Code "Backend" launch config
   builds into `/tmp/kidra-debug-bin`, so Automigrate also works while debugging.

2. Start the app:

   ```sh
   cd frontend
   pnpm install
   pnpm dev
   ```

   In dev mode the app talks to `http://127.0.0.1:8090` (see `src/lib/data/client.ts`). In a
   production build it uses relative URLs, because the backend serves the app itself.

`.vscode/launch.json` has a "Backend (PocketBase)" Go configuration (`serve` in
`backend/`), a "Frontend (vite dev)" configuration, a Chrome configuration for
http://localhost:5173 and a "Debug All" compound that starts all three.

To try the production setup locally, run `pnpm build` (writes `backend/ui/dist/`) and
restart the backend: without `-tags embedui` it serves `./ui/dist` when that exists.

## Scripts (in `frontend/`)

| Script         | What it does                                                                                                                             |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm dev`     | Vite dev server with hot reload.                                                                                                         |
| `pnpm build`   | Static SPA build into `backend/ui/dist` (with an `index.html` fallback for deep links). The folder is replaced on every build.          |
| `pnpm preview` | Serves the last build locally.                                                                                                           |
| `pnpm check`   | `svelte-kit sync` plus `svelte-check` type checking.                                                                                     |
| `pnpm lint`    | Prettier check plus ESLint (frontend only).                                                                                              |
| `pnpm format`  | Formats the frontend with Prettier.                                                                                                      |
| `pnpm test`    | Runs the Vitest unit tests once (`pnpm test:watch` to keep watching).                                                                    |
| `pnpm types`   | Regenerates `src/lib/data/pocketbase-types.ts` from `backend/pb_data/data.db`. Run it after changing a collection, and commit the result. |

Backend checks (in `backend/`): `gofmt -l .`, `go vet ./...`, `go test ./...`.

Before committing, run `pnpm check`, `pnpm lint` and `pnpm test`, plus the backend checks
when you changed Go code. CI runs the same (`.github/workflows/ci.yml`).

## Production builds

Every variant contains the same binary, with the SPA embedded (`-tags embedui`), and the
`pb_migrations/` directory next to it.

- **Docker images on GHCR** (`ghcr.io/<owner>/kidra`), built by CI:
  - `full` (default): based on the official `kicad/kicad` image, includes kicad-cli.
    Tags `:vX.Y.Z`, `:X.Y`, `:latest`, `:prod` (releases), `:dev` and `:sha-<7>` (main).
  - `slim`: distroless, no kicad-cli (no SVG previews). Same tags with a `-slim` suffix.
  - Both run as uid 1000, keep their data in `/pb_data` and listen on 8090.
- **Compose quick start:**

  ```sh
  cp .env.example .env        # optionally pin KIDRA_IMAGE to a version
  mkdir -p pb_data && sudo chown 1000:1000 pb_data
  docker compose up -d        # optional: kidra.env and secrets.env next to compose.yaml
  ```

  To build the image locally instead:
  `docker compose -f compose.yaml -f compose.build.yaml up -d --build`
  (`KIDRA_TARGET=slim` for the slim image), or `docker build [--target slim] .`.

- **Native archives** on GitHub Releases: `kidra_<version>_linux_amd64.tar.gz`,
  `…_linux_arm64.tar.gz` and `…_windows_amd64.zip`. Each contains `kidra[.exe]`,
  `pb_migrations/` (keep it next to the binary), this README, `kidra.service` and
  `windows.md`. kicad-cli is optional: install KiCad and set `KIDRA_KICAD_CLI` if it is not
  on `PATH`. See `deploy/native/` and [deploy/README.md](deploy/README.md).

Building a binary by hand:

```sh
cd frontend && pnpm build && cd ../backend
CGO_ENABLED=0 go build -tags embedui -trimpath \
  -ldflags "-X main.version=v1.2.3 -X main.commit=$(git rev-parse HEAD)" -o kidra .
```

On top of PocketBase, `kidra` has `kidra health [--url …] [--timeout …]` (exit code 0/1 for
`GET /api/health`, used by the container `HEALTHCHECK`) and the public
`GET /api/kidra/info` (`version`, `commit`, `kicadCli`, `kicadVersion`).

## Configuration

All settings are optional environment variables of the backend; `.env.example` is the
annotated reference. Besides the real environment (compose `env_file`, systemd
`EnvironmentFile`), the backend reads a dotenv file at start-up: `KIDRA_ENV_FILE`, else
`<data dir>/kidra.env`. Variables that are already set in the environment always win. The
data directory is PocketBase's `--dir` (`/pb_data` in the images).

| Variable                        | Default                                                        | What it does                                                                                                                                                                                                                                                        |
| ------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `KIDRA_ENV_FILE`                | `<data dir>/kidra.env` (skipped if missing)                    | Dotenv file to load. If set explicitly, a missing file is a start-up error.                                                                                                                                                                                         |
| `KIDRA_MIGRATIONS_DIR`          | `<exe dir>/pb_migrations` if it exists, else `./pb_migrations` | Directory of the JS migrations. The images set `/app/pb_migrations`.                                                                                                                                                                                                |
| `KIDRA_PUBLIC_DIR`              | embedded UI, else `./ui/dist`                                  | Serve the SPA from this directory instead. Without any UI only the API is served (logged as a warning).                                                                                                                                                             |
| `KIDRA_APP_URL`                 | unset                                                          | Public base URL (PocketBase `meta.appURL`). Applied once by the bootstrap migration.                                                                                                                                                                                |
| `KIDRA_TRUSTED_PROXY`           | unset                                                          | `1`/`true`/`yes`/`on` makes PocketBase take the client IP from `X-Forwarded-For` (set it behind a reverse proxy only). Applied once by the bootstrap migration.                                                                                                       |
| `KIDRA_ADMIN_EMAIL`             | unset                                                          | Together with `KIDRA_ADMIN_PASSWORD`: superuser created (or its password reset) by the bootstrap migration. Both must be set.                                                                                                                                      |
| `KIDRA_ADMIN_PASSWORD`          | unset                                                          | See above. Keep it in `secrets.env` or another 0600 file.                                                                                                                                                                                                           |
| `KIDRA_LIBRARY_REPO`            | the Gradur_Libraries_Test GitHub repo                          | Git URL of the KiCad symbol/footprint library repository.                                                                                                                                                                                                           |
| `KIDRA_LIBRARY_PATH`            | `<data dir>/repositories/project`                              | Where the repository is cloned.                                                                                                                                                                                                                                     |
| `KIDRA_LIBRARY_PULL_CRON`       | `*/5 * * * *`                                                  | Pull schedule; the libraries are only re-parsed when a pull brings changes. An invalid value logs an error and uses the default.                                                                                                                                   |
| `KIDRA_3DMODEL_DIR`             | `3dmodels`                                                     | Repo-relative directory that `${KICAD*_3DMODEL_DIR}` and `${KIPRJMOD}` in footprint model paths map to (`${KICAD_USER_BASE_DIR}` maps to the repo root).                                                                                                            |
| `KIDRA_KICAD_STOCK_3DMODEL_DIR` | first existing of `/usr/share/kicad/3dmodels` and others       | KiCad's stock 3D models. Versioned `${KICAD<n>_3DMODEL_DIR}` paths resolve there first and fall back to the repository; files must stay inside the directory (symlinks escaping it are refused). The full image sets `/kicad-3dmodels` (mount point in `compose.yaml`). |
| `KIDRA_KICAD_CLI`               | `kicad-cli` from `PATH`                                        | kicad-cli binary for symbol/footprint SVG previews. The full image sets `/usr/bin/kicad-cli`.                                                                                                                                                                       |
| `KIDRA_DOWNLOAD_ALLOW_PRIVATE`  | `false`                                                        | `true` lets the "download from URL" proxy (`/api/datasheet-download`) fetch from loopback/private networks (e.g. an intranet datasheet server). By default those addresses are refused.                                                                            |

Compose itself reads `KIDRA_IMAGE`, `KIDRA_PORT` (host port, default 8090) and
`KIDRA_TARGET` (for `compose.build.yaml`) from `.env` next to `compose.yaml`.

### Symbol and footprint previews (optional kicad-cli)

If kicad-cli is available, the backend renders an SVG of every symbol and footprint after
parsing the library repository and stores it in the record's `preview` field. Rendering runs
in the background and only for entries whose source changed (`sourceHash`). Without
kicad-cli the backend logs one warning at start-up, `preview` stays empty and the app shows
"No preview available"; everything else works. The parser also fills `pinCount` (symbols)
and `padCount` (footprints), which the checks page compares.

Footprint 3D models (`model3d`, the footprint's `(model …)` path) are served by
`GET /api/footprint-model/{id}` (and `…/info`) from the library repository or KiCad's stock
model directory, see `KIDRA_3DMODEL_DIR` and `KIDRA_KICAD_STOCK_3DMODEL_DIR` above.

## PocketBase settings

The bootstrap migration (`backend/pb_migrations/1795012700_bootstrap.js`) configures the
database once, on the first start:

- **Batch API** enabled with up to 100 requests. Saving a part first uploads each new
  attachment file in its own request, then writes the part, its ratings, distributor parts,
  new tags and attachment links in one atomic
  [batch request](https://pocketbase.io/docs/api-records/#batch-createupdateupsertdelete-records):
  one request per rating, distributor part, new tag, removed rating/distributor part and
  changed or link-only attachment, plus the part. Without the Batch API every part save
  fails. The batch body size limit does not matter, because the batch only carries JSON.
- App name "Kidra", app URL from `KIDRA_APP_URL`, `X-Forwarded-For` as trusted proxy header
  when `KIDRA_TRUSTED_PROXY` is `1`/`true`.
- Nightly backups at 03:00, keeping 7 (`<data dir>/backups/`).
- A superuser from `KIDRA_ADMIN_EMAIL` / `KIDRA_ADMIN_PASSWORD`.

Migrations run only once, so later changes to these variables have no effect. Change the
settings in the dashboard (`/_/` → Settings), and the admin password with
`kidra superuser upsert <email> <password> --dir=<data dir>`.

**Existing installs** (databases created before the bootstrap migration existed) get it
applied once on the next start, which overwrites the batch, app name and backup settings
above. Check **Settings → Application → Batch API** (enabled, max requests large enough
for the biggest part) and **Settings → Backups** in the dashboard afterwards.

Attachments (`attachments` collection) accept any file type up to **100 MB** (the `file`
field's max size). PocketBase sizes the request body limit of the record create endpoint from
that field, so no extra setting is needed; a reverse proxy in front must allow request bodies
of that size too (see `deploy/proxy/`). Downloads "from URL" go through the backend's
`/api/datasheet-download` proxy (logged-in users only, http(s) URLs only, also 100 MB;
private-network targets are refused unless `KIDRA_DOWNLOAD_ALLOW_PRIVATE=true`).

3D previews use [online-3d-viewer](https://github.com/kovacsv/Online3DViewer). Its STEP/IGES
importer (`occt-import-js`, ~8 MB WASM) is copied from `node_modules` into
`frontend/static/occt-import-js/` by a plugin in `frontend/vite.config.ts` (git-ignored) and
served locally; a `pnpm patch` (`frontend/patches/online-3d-viewer@0.18.0.patch`) makes the
viewer load it from there instead of a CDN. Draco-compressed glTF, 3DM and IFC files would
still load their decoders from a CDN; KiCad models (STEP, WRL) do not need them.

## Release process

Releases are managed by [release-please](https://github.com/googleapis/release-please)
from the commit messages on `main`; nobody creates tags by hand.

- **Pull requests** run `ci.yml` (frontend lint/check/test/build, backend gofmt/vet/test)
  and `docker-pr.yml` (builds both images, pushes nothing).
- **Merge to `main`** runs `main.yml`: CI, then `:sha-<7>` and `:dev` (plus `-slim`) are
  pushed to GHCR and the full image is deployed by digest to the **dev** VM. These builds
  report the version `<version.txt>+<sha7>` (e.g. `0.1.0+abc1234`: a commit after 0.1.0).
  In parallel, release-please opens or updates the **release PR** ("chore(main): release
  X.Y.Z"), which bumps `version.txt`, `frontend/package.json` and `CHANGELOG.md`.
- **Merging the release PR** is the release. On that push release-please creates the tag
  `vX.Y.Z` and the GitHub release (notes from the changelog); the image built for that
  commit reports `X.Y.Z`, is deployed to dev, and only after that succeeds `release.yml`
  (called from `main.yml`) retags the same digests as `:vX.Y.Z`, `:X.Y`, `:latest` and
  `:prod` (+ `-slim`), uploads the native archives and `SHA256SUMS` to the release, adds
  the image digests to the release notes and deploys the same digest to **prod**.
- **Re-running a release** (e.g. a failed upload or prod deploy): re-run the failed jobs
  of that `main` run, or start `release` manually (Actions -> release -> Run workflow, from
  `main`, with the tag). There are no prereleases.

Every deploy snapshots the VM first and rolls back if the new version does not come up
healthy; see [deploy/README.md](deploy/README.md).

## Contributing: commit messages

Commit messages on `main` (with squash merges: the PR title) must follow
[Conventional Commits](https://www.conventionalcommits.org/), because release-please
derives the next version and the changelog from them. Nothing checks this automatically.

| Type                                           | Version bump (before 1.0.0) | Version bump (from 1.0.0) | Changelog            |
| ---------------------------------------------- | --------------------------- | ------------------------- | -------------------- |
| `feat:`                                        | minor (0.1.0 -> 0.2.0)      | minor                     | Features             |
| `fix:`, `perf:`                                | patch                       | patch                     | Bug Fixes / Perf.    |
| `refactor:`, `docs:`, `deps:`, `revert:`       | patch                       | patch                     | own section          |
| `feat!:` / `BREAKING CHANGE:` footer           | minor                       | major                     | breaking changes     |
| `chore:`, `ci:`, `build:`, `test:`, `style:`   | none on their own           | none on their own         | hidden               |

A release PR only appears once there is at least one commit with a visible type since the
last release. To force a specific version, add a `Release-As: X.Y.Z` footer to a commit.
