# Architecture

A monorepo with two parts:

- `frontend/`: a SvelteKit single-page app (Svelte 5 runes, `ssr = false`) built with
  adapter-static into `backend/ui/dist`. All data comes from PocketBase through its JS SDK;
  the frontend has no server-side code.
- `backend/`: the Go module `kidra`, a custom PocketBase build that adds the library sync,
  kicad-cli previews, the KiCad HTTP library API and other routes, and serves the SPA (see
  [Backend and deployment](#backend-and-deployment)).

Unless noted otherwise, paths in the frontend sections are relative to `frontend/`.

## The layer rule

```
routes/            renders pages, wires data to components
  │        │
  ▼        ▼
lib/data/  lib/components/        lib/components/ui/
talks to   reusable UI,     ───▶  shadcn-svelte primitives
PocketBase no PocketBase          (generated, not edited)
```

- **`src/routes`** renders. A page creates its data (`createCollection`, `savePart`, …),
  configures components and handles user actions. Page-specific helpers live next to the page
  (e.g. `parts/part-dialog/`).
- **`src/lib/data`** is the only code that talks to PocketBase. It owns the client, auth,
  generated record types and all reads/writes.
- **`src/lib/components`** is reusable UI. It takes data and callbacks as props and does not
  import PocketBase. The one exception is `app-shell/` (sidebar, user menu, login form),
  which calls `lib/data/auth.svelte.ts` for login, logout and the current user.
- **`src/lib/components/ui`** is [shadcn-svelte](https://shadcn-svelte.com). Never edit these
  files by hand: add or update a component with `pnpm dlx shadcn-svelte add <name>` and wrap
  or compose it in `lib/components` if you need different behaviour. Prettier and ESLint skip
  this folder.

The part dialog (`routes/app/application/parts/part-dialog/`) is split into
`part-dialog-content.svelte` (the form), `part-form.svelte.ts` (`PartFormState`: fields,
validation, `toPart()`), `part-schema.ts` (zod schema), `part-lookups.svelte.ts` (the
collections the dropdowns need), `editable-rows.svelte.ts` (rating / distributor rows),
`sections/` (one component per accordion section) and `attachments/` (the attachment list
state, the attachments panel with the dialog's single preview pane, and the picker for
existing attachments).

## Data flow

### Collections

`createCollection<T>(name, { label, listOptions })` in `lib/data/collection.svelte.ts` returns
reactive `data` and `loading` plus `load()`, `create(rows)`, `update(rows)` and
`remove(row)`.

- Each operation catches its own errors, shows them as a toast through `notify.error`
  ("Failed to update category: …") and resolves to `true` or `false`. It never throws.
- After a successful write, `data` is updated from the server response, so pages do not
  reload after every edit. `listOptions.expand` is also requested on writes, so expanded
  relations stay filled.

### Editable tables

`DataTable` and `TreeTable` (`lib/components/data-table/`) are built on TanStack Table.
Columns come from `createColumns(configs)` in `columns.ts`; each config has a `header`, an
`accessor`, a `type` and optional `editable` / `searchable` flags.

Inline editing is handled by `TableEditState` (`edit-state.svelte.ts`): one row at a time
is edited on a draft copy, and cells register changes through a Svelte context
(`context.ts`). On save the table calls `onCreate(row)` for a new row or `onUpdate(row)` for a
changed one. If the handler returns (or resolves to) `false`, the row stays in edit mode with
the user's changes, so pages simply pass the collection's result through:

```svelte
<DataTable
	data={categories.data}
	{columns}
	createRow={newCategory}
	onCreate={(row) => categories.create([row])}
	onUpdate={(row) => categories.update([row])}
/>
```

`TreeTable` takes the same columns plus `getSubRows`. Tree rows are built with `buildTree` /
`buildLibraryTree` (`lib/data/library-tree.ts`), which tag each row with `kind: 'group' |
'item'`; strip those fields with `treeRecord()` before writing a row back.

### Attachments

Files of a part live in the shared `attachments` collection (name, `file`, source `url`,
`kind`: datasheet / reference-manual / app-note / 3d-model / image / other, `description`).
They are library records: a part links any number of them through `parts.attachments`, and
several parts can link the same one. `parts.datasheet` is the **primary datasheet** (KiCad's
single `Datasheet` field); it is always one of the linked attachments or empty.

In the part dialog, `AttachmentListState` (`attachments/attachment-list-state.svelte.ts`)
holds the rows, the primary datasheet, the selected row and per-row upload progress.
`attachments-panel.svelte` lists the rows grouped by kind and holds the dialog's **only
preview pane**: whatever is selected becomes a `PreviewSource` (`{ kind, src, name }`) for
`AttachmentPreview` from `lib/components/preview/`. Entries that are not attachments (e.g.
the part's symbol or footprint) are passed to the panel as `extraItems: PreviewEntry[]`; they
are listed under their own `group` heading, selected the same way and previewed in the same
pane. `AttachmentPreview` has no PocketBase dependency, so other pages can reuse it.

### Symbol, footprint and 3D previews

The backend renders `preview` SVGs of symbols and footprints with kicad-cli when it is
installed (otherwise the field is empty and the UI says "No preview available"), and serves
footprint 3D models through `/api/footprint-model/{id}`. `lib/data/kicad-previews.ts` builds the
SVG URLs and fetches the model; the model route needs the `Authorization` header, so the model
is fetched as a blob and shown through an object URL.

- **Part dialog:** `part-dialog-content.svelte` passes three `extraItems` under the heading
  "KiCad": _Symbol_ and _Footprint_ (SVG) for the symbol/footprint currently chosen in the form,
  and _Footprint 3D_, which is only listed when `/info` reports a model. They follow the form
  reactively. `FootprintModelState` checks `/info` whenever the footprint changes but downloads
  the model only while the _Footprint 3D_ entry is selected; switching footprints aborts
  pending requests, ignores late answers and revokes the object URL.
- **Master data:** the symbols and footprints pages select a row with `onRowClick` and show it
  in a `PreviewPanel` beside the table (below it on narrow screens). The footprints panel has a
  2D/3D switch backed by the same `FootprintModelState`. Both tables show `pinCount` /
  `padCount` read-only.

### Integrity checks

`checkParts()` (`lib/data/checks.ts`, pure and unit-tested) reports per part: an **error** when
its symbol or footprint is unset, deleted, or `available === false` (gone from the library
repository), and a **warning** when the symbol's `pinCount` and the footprint's `padCount` are
both known (> 0) and differ (legitimate for thermal/mounting pads and NC pins).
`createPartChecks()` loads the three collections (only the needed fields) and runs no checks
when a load failed, so a missing list cannot turn into false errors. The checks page lists the
issues with a link to `/app/application/parts?part=<id>`, which opens the part dialog.

### Saving a part

A part references ratings, distributor parts, tags and attachments that are edited in the
same dialog. `lib/data/parts.ts` saves them in two steps:

1. The dialog validates and submits a `PartDraft` (the part record from
   `PartFormState.toPart()` plus the rating, distributor part, tag and attachment drafts and
   the primary datasheet id).
2. `savePart()` uploads every attachment draft with a new file, one request each
   (`uploadAttachment()`, an `XMLHttpRequest` so the dialog can show progress). It writes
   the new record id into the draft, so a retry does not upload again. If the save fails
   later, the uploaded files simply stay in the attachment library.
3. `planPartSave()` turns the draft into a list of create/update/delete operations without
   sending anything. New records get client-generated ids so the part can reference them in
   the same batch; ratings and distributor parts the part no longer uses are deleted.
   Attachments are only linked (their metadata is updated when it changed) and never
   deleted. This function is pure and unit-tested (`parts.test.ts`).
4. `savePart()` sends the operations with `pb.createBatch()`. Either everything is written or
   nothing is, so on failure the page shows a toast and keeps the dialog open for a retry.

This needs the Batch API enabled in PocketBase; the bootstrap migration does that (see
README, "PocketBase settings").

## Auth

- `lib/data/auth.svelte.ts` mirrors `pb.authStore` into a reactive `auth` object (`isValid`,
  `record`, …) and exports `login`, `logout` and `avatarUrl`. The SDK keeps the token in
  `localStorage`.
- `routes/app/+layout.ts` redirects to `/login` when `auth.isValid` is false. It runs when
  navigating into `/app`, so code that logs out also navigates to `/login` itself (see
  `nav-user.svelte`).
- `routes/login/+page.ts` sends logged-in users on to `/app/master-data`.

## How to

### Add a master-data page

1. Create the collection in the dashboard of the dev backend (`go run . serve`, so
   Automigrate writes a migration into `backend/pb_migrations/`; commit it), then run
   `pnpm types`.
2. Copy `src/routes/app/master-data/categories/+page.svelte` to
   `src/routes/app/master-data/<name>/+page.svelte`. Change the record type, the collection
   name and label, the columns and the `new…()` row factory.
3. Add an entry under "Master Data" in `src/lib/navigation.ts` (this also sets the page title
   in the header).
4. Optionally add a card to the `cards` array in `src/routes/app/master-data/+page.svelte`.

For a relation column, use `type: 'combobox'` with `options` and a `labelAccessor` such as
`'expand.distributor.name'`, and pass `listOptions: { expand: '…' }` to `createCollection`
(see `parts/part-dialog/sections/distributors-section.svelte`). For grouped data, start from
`units`, `symbols` or `footprints`, which use `TreeTable`.

### Add a column type to the data table

1. Add the name to the `ColumnType` union in `data-table/columns.ts` (and any new config
   options to `ColumnConfig`).
2. Display: add a snippet to `cells/display-cells.svelte` and a case to `renderDisplay()` in
   `columns.ts`. If the value people search or sort by differs from the raw value, handle it
   in `searchValue()`.
3. Editing (if the type is editable): add an editor branch to `cells/editable-cell.svelte` and
   convert the value in `toInputValue()` / `fromInputValue()`. Pass any extra props from the
   `renderComponent(EditableCell, …)` call in `createColumns()`.
4. Add tests to `columns.test.ts`.

### Add a field to parts

1. Add the field to the `parts` collection in the dev backend's dashboard (commit the
   migration Automigrate writes) and run `pnpm types`, so `PartsRecord` has it.
2. `part-form.svelte.ts`: add a `$state` field, load it in `reset()` and write it in
   `toPart()`.
3. `part-schema.ts`: only if it needs validation. Add it to the schema and to
   `#currentData()` in `part-form.svelte.ts`; required fields also go into `submitFields`.
4. Bind an input to `form.<field>` in the right component in `part-dialog/sections/`
   (respect `readOnly`).
5. `planPartSave()` copies every field of the part record, so a plain field needs no change
   there. Only a relation to records created in the same save (like `ratings`) needs new
   operations, plus tests in `parts.test.ts`.
6. Optionally show it as a column in `parts/+page.svelte`, and expose it to KiCad in the
   backend (`backend/api_v1.go`).

## Conventions

- Files and URLs are kebab-case (`row-actions-menu.svelte`, `/app/master-data`). Files with
  runes outside components end in `.svelte.ts`.
- Components and types are PascalCase; functions and variables are camelCase.
- Use string unions (`'create' | 'edit' | 'view'`) instead of enums.
- Icons come from `@lucide/svelte`.
- Import from `src/lib` with the `#lib/...` alias (e.g. `#lib/data/collection.svelte.ts`),
  not long relative paths.
- Tests sit next to the code as `*.test.ts`, or `*.svelte.test.ts` when they use runes. They
  run in Vitest and cover logic only (column building, edit state, part save planning, …),
  not rendered components.
- User-facing errors go through `notify` (toasts); `lib/data` functions report their own
  failures or document what they throw.

## Backend and deployment

### Serving the SPA

The backend binary serves the SPA under `/` (`backend/static.go`). The source is, in this
order: `KIDRA_PUBLIC_DIR`, the copy embedded at build time with `-tags embedui`
(`ui_embed.go`; without the tag `ui_noembed.go` embeds nothing), or `./ui/dist` when it
exists. With none of them only the API is served. The catch-all `GET /{path...}` route:

- answers unmatched `/api/*` and `/kicad-api/*` requests with a JSON 404, never with the app,
- answers a missing `/_app/*` file (e.g. a stale hashed chunk after a deploy) with 404
  instead of `index.html`, which the browser would fail to parse as JS/CSS,
- falls back to `index.html` for everything else (client-side routes),
- sends `Cache-Control: public, max-age=31536000, immutable` for existing files under
  `_app/immutable/` and `no-cache` for everything else, so `index.html` is always
  revalidated.

### Migrations and settings

The schema lives in JS migrations in `backend/pb_migrations/`, run by PocketBase's jsvm
plugin on every `serve` (`backend/migrations.go`). jsvm is used only for migrations:
`pb_hooks` are never loaded, all app logic is Go. The directory is `KIDRA_MIGRATIONS_DIR`,
else `<exe dir>/pb_migrations`, else `./pb_migrations`. Automigrate (a migration file per
dashboard schema change) is on only when the executable runs from the temp dir, i.e. under
`go run`.

Two migrations matter for new databases: `1795012391_schema_catchup.js` imports collections
that were once edited in the dashboard without a migration (it does nothing when the schema
is already complete), and `1795012700_bootstrap.js` sets the instance settings (Batch API,
app name/URL, trusted proxy, backups, superuser from `KIDRA_ADMIN_*`) once.

### Configuration and runtime info

`main.go` loads a dotenv file (`KIDRA_ENV_FILE`, else `<data dir>/kidra.env`,
`backend/envfile.go`) before anything else and never overrides variables already set. It is
meant for native installs; containers get their environment from compose `env_file`.

`backend/version.go` adds the public `GET /api/kidra/info` (`version` and `commit`, set by
`-ldflags -X main.version=… -X main.commit=…`, plus whether kicad-cli is available and its
version) and the `kidra health` command, which exits 0 when `GET /api/health` answers 200.
It runs without opening the data dir, so the distroless image can use it as `HEALTHCHECK`.

### Images

The root `Dockerfile` builds the SPA (`web` stage), then a static Go binary with the SPA
embedded (`gobuild`), and produces two targets:

```
/app/kidra            the binary (ENTRYPOINT; CMD serve --http=0.0.0.0:8090 --dir=/pb_data)
/app/pb_migrations/   KIDRA_MIGRATIONS_DIR
/pb_data/             data volume, owned by uid 1000 (the image user)
```

- `full` (default): `FROM kicad/kicad:10.0.x` pinned by digest, user `kicad` (uid 1000),
  with kicad-cli (`KIDRA_KICAD_CLI=/usr/bin/kicad-cli`) and
  `KIDRA_KICAD_STOCK_3DMODEL_DIR=/kicad-3dmodels` (a mount point; the image has no 3D
  models). Sudo is removed.
- `slim`: distroless static, uid 1000, no kicad-cli.

### CI/CD

```
pull request ──► ci.yml (frontend + backend checks) + docker-pr.yml (build full/slim, no push)

push main ──► main.yml
               ├─ ci.yml
               ├─ release-please: open/update the release PR
               │    (version.txt, frontend/package.json, CHANGELOG.md)
               │    merged release PR ──► tag vX.Y.Z + GitHub release
               ├─ image (needs ci, release-please): build full + slim
               │    ──► GHCR :sha-<7>, :dev (+ -slim)
               │    VERSION = X.Y.Z on a release commit, else <version.txt>+<sha7>
               ├─ deploy-dev (self-hosted runner, label kidra-deploy)
               │    deploy/ci/deploy.sh dev ghcr.io/<owner>/kidra@sha256:… <sha>
               │      │ ssh deploy@VM (forced command kidra-deploy)
               │      ├─ status, prepare (ship compose.yaml + kidra.env, docker pull)
               │      ├─ stop app
               │      ├─ PVE API: snapshot predeploy-<time>-<digest12>
               │      ├─ up: docker compose up -d, wait for container healthy
               │      ├─ poll /api/health + /api/kidra/info .commit == <sha>
               │      ├─ ok   ──► prune old predeploy-* snapshots
               │      └─ fail ──► PVE rollback to snapshot, start VM + previous app, exit 1
               └─ release ──► release.yml (workflow_call; only if release-please
                    │          created a release, after deploy-dev succeeded)
                    ├─ prepare: validate tag, resolve commit
                    ├─ image: retag the digests ──► :vX.Y.Z, :X.Y, :latest, :prod (+ -slim)
                    ├─ ui + binaries: linux/amd64, linux/arm64, windows/amd64 archives
                    ├─ publish-release: SHA256SUMS, gh release upload --clobber,
                    │    image digests appended to the release notes
                    └─ deploy-prod: same deploy.sh flow against the prod VM

manual ──► release.yml (workflow_dispatch from main, input tag vX.Y.Z): same jobs for an
           existing release; reuses :sha-<7> or rebuilds if it is missing
```

Tags and releases created by release-please with the default `GITHUB_TOKEN` do not
trigger other workflows, which is why the release runs inside `main.yml` instead of on
`push: tags`. A GitHub App token for release-please would change that if it is ever needed.

Operator details (VM provisioning, PVE token, runner, environments, backups) are in
[deploy/README.md](deploy/README.md).
